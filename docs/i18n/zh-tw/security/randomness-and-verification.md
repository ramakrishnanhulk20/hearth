# 隨機性與驗證

一次抽獎只有在陌生人查核得了的時候才有價值。這一頁講的就是怎麼查。

## 種子從哪裡來

一個呼叫，就在截止那一期抽獎的交易裡：

```solidity
euint64 seed = FHE.randEuint64();
```

那是在 Zama 的協同處理器裡執行的。這個數字由一個密碼學安全的產生器，在網路的 FHE 金鑰之下產生，
而回到合約手上的是一個密文 handle，不是數字。那一刻沒有人看過它的值：呼叫者沒有，我們沒有，礦工
也沒有。

Zama 產生器有兩個性質在這裡很重要，而且兩個都寫在 Zama 自己的文件裡：

- **它必須在交易裡執行。** 產生一個隨機值會改動鏈上的產生器狀態，所以它沒辦法透過 `eth_call`（模擬
  呼叫的唯讀方式）完成。沒有人能在鏈下預覽一期抽獎，看看自己會不會中。
- **它是密碼學安全的，而且保持加密**，直到有東西明確把它變成可解密為止。

## 為什麼沒人能重擲它，或改動它能贏到的金額

四件事，合起來。

1. **截止只會成功一次。** 抽獎的狀態機每期只允許 `closeDraw(p)` 一次。沒有第二次機會去買一個更好的
   數字。
2. **抽出來的時候值是未知的。** 既然種子在建立時就是密文，送出截止交易的人不會因為送了這筆交易而
   學到任何東西。搶著當呼叫者沒有意義。
3. **公布這一步是單向的。** 截止之後，種子被標為可公開解密。那個旗標在 Zama 的存取控制清單上是永久
   而且不可撤銷的，所以世界看到的那個數字，就是合約先前承諾的那個，不是事後挑的。
4. **獎金在種子存在之前就固定了。** 每個層級的獎金金額和它拿出來的資金，都在同一筆截止交易的最前面
   算好，發生在 `randEuint64` 被呼叫之前。在早期草案裡它們是稍後在開獎時才設定的，那留下一個窗口，
   讓某人可以讀到種子、算出自己中了獎，再把資金在各層級之間搬動，好讓那次中獎更值錢。那個窗口沒有
   了。

拿它跟其他設計比一比。以區塊雜湊餵養的抽獎，可以被一個不喜歡結果的驗證者重擲。以鏈下數字餵養的抽獎，
可以直接被挑出來。這兩件事在這裡都不可能，而這正是隨機性要在鏈上、在加密狀態下產生，而絕不由鏈下
產生器產生的全部原因。

## 什麼會變公開，以及何時

| 數值 | 何時公布 | 為什麼它必須公開 |
| --- | --- | --- |
| 種子 `R` | 截止時，中繼器解密後可讀 | 沒有它，沒有人重算得出門檻 |
| 尺度計數，由它得出級距 `M` | 截止時 | 門檻是相對於資金池規模而定的 |
| 該期是否非空 | 截止時 | 用來區分空的一期和真的有人的一期 |
| 該期的收成 | 截止時 | 那是支付後續獎金的錢 |
| 各層級的獎金金額和它拿出來的明文資金 | 截止時 | 用來查核一次中獎付多少 |
| 各層級的結轉金 | 每期定案時，因為每個層級每期都對帳 | 用來查核該層級付了幾份獎 |
| 未撥付計數器 | 定案時 | 證明資金池為金庫寫下的每一筆入帳都撥了款 |

有兩樣東西刻意**不在**那份清單上。資金池精確的時間加權餘額總和永遠不公布，因為那樣做會讓旁觀者精確
還原出一位落單者的存入金額；公布的是它上方的級距。而且任何逐人的數值都不會被標為可公開解密。

清單上的每一項，都是在它所決定的那一期已經結束之後才出現。公布 `R` 幫不了任何人改變權重，因為第 `p`
期的權重在第 `p` 期結束的那一刻就凍結了，而那還在該期抽獎能被截止之前。

那些數字每一個抵達合約時，都帶著 Zama 金鑰管理服務的簽章，由 `FHE.checkSignatures` 在鏈上驗證。證明
以固定順序綁在那些 handle 上：開獎時是 `[seed, scaleCount, nonEmpty, harvested]`，對帳時則是每次一個
結轉金 handle。沒有東西能在欄位之間被調換，也沒有東西能被重放到另一期抽獎。抽獎的狀態機就是防重放
機制：每一步每期只成功一次，而對帳每個層級只成功一次。

## 級距，以及金庫怎麼追蹤它

一期資金池的時間加權餘額總和 `W` 保持加密。抽獎實際跑的對象是 `M = 2^m`，也就是大於或等於 `W` 的
最小 2 的冪。

金庫是一期一期追蹤 `m`，而不是每次從頭算。每次截止時，它在加密狀態下把 `W` 跟前一期 `m` 周圍的五個
2 的冪比較，把五個結果加成一個加密的小型計數，再把那個計數標成可公開解密。資金池讀取驗證過的計數，
算出新的 `m`，而 `m` 每期最多移動三階。另一個獨立的加密比較（跟 1 比）給出非空旗標。

所以每期的公開紀錄就是一個小整數，而且只有在池子跨過一個 2 的冪時才會變。資金池上的 `scaleBits()`
讀出目前的 `m`；部署時以 `initialScaleBits` 作為起始值，也就是第一期總額預期的位元長度，而追蹤器
每期最多修正三個位元的誤差。

## 任何人怎麼重算一個門檻

以下全部只用公開資料。不用錢包、不用簽章、不用權限。

對第 `p` 期抽獎、存戶位址 `u`、有 `count[t]` 份獎、機率為 `oddsNum[t] / oddsDen[t]` 的層級 `t`：

```
prn         = keccak256(abi.encode(R, p, u, t))
r           = prn mod M                                        // 0 <= r < M
threshold_k = floor((r + k * M) * oddsDen[t] / (oddsNum[t] * count[t]))
```

對每一個從 `0` 到 `count[t] - 1` 的 `k`。當且僅當該存戶在第 `p` 期的時間加權權重嚴格大於
`threshold_k` 時，他中了第 `k` 份獎。

你不必自己重寫一遍。金庫把 `thresholdOf(drawId, saver, tier, k)` 以 pure view 的形式公開，用的是跟
評估同一套算術，所以 App 的驗證面板、測試套件，以及任何有區塊瀏覽器的人，讀的都是同一份實作。如果你
寧可拿合約跟自己的程式碼對照，在鏈下重寫它也就是四行大整數算術。

用小數字寫的實例在[中獎判定](../concepts/winner-selection.md)。這裡則是一個來自真實 Sepolia 抽獎的
填好版本，取自 `usdc` 池，它的獎金池是 `0xA0785AacF30B6FE46EDc53CD8A9db1d94FeF5Df2`。每個池都為自己
的抽獎公布同樣的欄位：

| 欄位 | 數值 |
| --- | --- |
| 抽獎 | `2, the period from 23:00 to 00:00 UTC on 2 September 2026` |
| 種子 `R` | `5625525180683981523` |
| 級距 `M` | `2^43, which is 8,796,093,022,208 balance-seconds` |
| 收成 | `19.531380 USDC` |
| 各層級獎金金額 | `3.559644 / 1.779822 / 0.889911 USDC, grand / mid / frequent` |
| 各層級派出的獎項數 | `0 / 0 / 5, against a funded capacity of 2 / 2 / 8` |

從鏈上讀出：種子和級距來自資金池的 `DrawAwarded` 事件，獎金金額和拿出來的資金來自 `drawParams(2)`，
而派出的獎項數來自該期那三個 `TierReconciled` 事件，因為一個層級拿出來卻沒付掉的部分，正好就是它
公布的結轉金。這一期頭獎和中型獎層級都沒派出任何獎，把整筆拿出來的金額全數交回，而那正是一個
24 分之 1 和一個 6 分之 1 的層級大多數時候會做的事。

App 的驗證面板會在瀏覽器裡，為你輸入的任何位址做這套算術，網址是你想看的那個池的
`/verify?pool=<slug>`。它沒有任何特權存取；用的是同樣的公開輸入和同樣的公式。

## 為什麼取餘數沒有偏差

用單純的取餘數把一個大隨機數縮進某個範圍，通常會有偏差。如果 `2^256` 不是那個範圍的整數倍，比較小的
餘數會稍微常出現一點，而那個偏差會不均勻地落在存戶身上。PoolTogether V5 用拒絕採樣解決它，Hearth
早期的草案也是。

Hearth 現在不需要了。`M` 依結構就是 2 的冪，而 `2^256` 是每一個不超過 `2^256` 的 2 的冪的整數倍。
所以 `prn mod M` 就只是一個 256 位元雜湊的低 `m` 個位元，而從 `0` 到 `M - 1` 的每一個值，都來自數量
完全相同的輸入。**偏差是零，不是很小**，沒有迴圈、沒有拒絕，也沒有東西需要驗證者小心翼翼地重現。

那是「公布級距而不是精確總額」帶來的附帶好處，值得寫出來，因為它拿掉了一段程式碼，否則任何要查核
抽獎的人都得一模一樣地照做一遍。

## 磨位址沒有用

`R` 一旦公開，有人可以不斷生成位址，直到找到一個門檻很低的。那沒有用。門檻是拿來跟第 `p` 期的權重
比較的，而一個全新的位址在第 `p` 期或之前沒有任何觀測值，所以它的權重是零。零超不過任何門檻。要在
第 `p` 期有權重，你就得在第 `p` 期持有餘額，而那一期在 `R` 存在之前就結束了。

為未來某一期磨位址失敗的理由不同：那一期的種子還沒生成，而且它不可預測。

## 驗證證明了什麼、又沒有證明什麼

把這件事講精確，正是這一頁的目的。

**它證明了：**

- 種子是在鏈上、在一筆交易裡、在網路金鑰之下產生的，而且只公布過一次。
- 獎金金額和拿出來的資金，是在那個種子存在之前就固定的。
- 套用在每位存戶身上的規則是公開的、一致的，而且任何人都重算得出來。
- 獎金金額由層級資金和層級參數，透過公開算術推導而來。
- 每個層級派出的獎項數，符合「它拿出來的金額減去以結轉金形式回來的金額」。
- 資金池為金庫寫下的每一筆入帳都撥了款，因為未撥付計數器有公布，而且是零。

**它沒有證明：**

- 協同處理器的產生器是均勻的。那是 Zama 的引擎，它是被信任的，不是在這裡被驗證的。
- 金鑰管理服務簽的是種子 handle 真正的明文。合約檢查的是簽章，不是語意。一個不誠實的法定人數群組
  可以簽出自己挑的值。這個協定上的每一個應用都共用這項假設；它是[威脅模型](threat-model.md)裡的
  攻擊者 8。
- 公布的級距真的是所有存戶權重總和的級距。外部人加不起加密的權重，現在也看不到那個總和。他們手上有
  的，是同一份公開、不可變更的程式碼，用同一批觀測值算出了那些比較和每位存戶的權重，以及那些守恆
  不變量成立：已付等於已入帳，而且沒有人提領得比本金加獎金更多。
- 任何關於誰中獎的事。那正是全部的重點，也是為什麼公布得更多會讓驗證更強、卻讓產品更差。精確公布
  總額就是具體的例子：它讓池子的規模查核得了，同時也讓一位落單者的存入金額被還原到基本單位。

## 存戶查得到、而別人查不到的東西

存戶可以比外部人多走一步，因為他解得開自己在某一期的權重和自己的入帳金額。

1. 揭露你在第 `p` 期的權重。
2. 從公開的 `R` 和 `M` 重算你自己的門檻，或者直接從 `thresholdOf` 讀出來。
3. 數一數你超過了幾個，再乘上該層級的獎金金額。
4. 揭露你在第 `p` 期的入帳金額，檢查它對得上。

如果對不上，那要嘛是某個層級在巡走走到你之前就派完了（也就是那個有記載的設限），要嘛就是哪裡出了
問題，而你手上有數字可以證明。App 會替你做完這四步，並把算術顯示出來。

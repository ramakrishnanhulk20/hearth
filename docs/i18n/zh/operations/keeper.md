# keeper

开奖不会自己发生。得有个东西去发那些交易。本页讲的就是那个东西做什么、它停下时会怎样，以及它要花多少钱。

一个进程驱动一个池。Hearth 在 Sepolia 上跑七个池，所以有七个 keeper 进程在跑，
每一个用同一句助记词的自己那个账户签名，每一个指向一个池的地址文件。
下面「一池一个 keeper」那一节就是对照表。

先说重要的定位：keeper 没有任何特权。它调用的每一个函数任何人都能调用，
而一个 keeper 本可能滥用的那两根杠杆，也就是挑选谁被评估和挑选支付顺序，现在都不再是杠杆了。
它是一种给储户省事的便利，而不是这个池子在安全性上依赖的一个角色。

## 工作内容，按顺序，针对第 `p` 期开奖

1. **关闭。** 在周期 `p` 已经结束、并且在 `closeDeadline(p)` 也就是周期 `p+2` 的中点之前，
   调用 `closeDraw(p)`。习惯上在周期 `p+1` 的早期做是对的。
   这一步定死每个档位的奖金金额和拿出的流动性、把那笔流动性移进本期开奖、摇出加密种子、
   向金库索取加密的规模计数和非空标志、收割收益来源，并把那四个句柄全部标记为可公开解密。
2. **取回证明。** 请求 Zama 的中继器按
   `[seed, scaleCount, nonEmpty, harvested]` 的顺序公开解密这四个句柄。
   中继器返回明文，并附上密钥管理服务的签名。
3. **发奖。** 调用 `awardDraw(p, seed, scaleCount, nonEmpty, harvested, proof)`。
   合约在链上验证签名、把收割额记入各档位，并开启这期开奖。中奖者在这一刻被决定。
4. **评估。** 在金库上反复调用 `evaluate(p, count)`，直到遍历绕回它开始的地方。
   每次调用都把一个每期独立的游标沿储户名单往前推，起点由种子推导而来。
   keeper 挑的是 `count`，从来不是哪些地址；`4` 是一笔交易里装得下的、需要做加密运算的储户数上限。
   在周期 `p` 或之前没有观测点的储户，由合约自己从明文时间戳跳过，不产生任何加密开销。
5. **终结。** 在窗口于周期 `p+2` 结束时关闭之后，调用
   `finalizeDraw(p)`。这一步把每个档位未派出的余额折进该档位的加密结转额、
   公布未足额计数器，并为每一个到期对账的档位把结转额标记为可公开解密，同时发出 `CarryPublished`。
6. **逐个到期档位对账。** 对 `finalizeDraw` 公布的每一个档位，取回结转额明文并调用
   `reconcile(tier, carry, proof)`。资金池对照金库公布的句柄检查证明，
   把验证过的数字记入该档位的明文流动性，金库从结转额（它自公布以来可能已经增长）里减去它，
   随后发出 `TierReconciled`。

在 Sepolia 上，每个池的每个档位每期都到期，所以第 6 步在每次终结之后最多跑三次。
这个节奏是一个每档位的构造函数参数，而 keeper 是从链上读它而不是假定它，
所以一个更少公布某档位结转额的部署，不需要改动 keeper。
这一版为什么每期公布全部三个，见
[奖金与档位](../concepts/prizes-and-tiers.md)。

## 执行顺序规则

**在周期 `p+3` 的开头先给第 `p` 期做终结和对账，再在同一个周期里关闭第 `p+2` 期。**

理由是钱，不是正确性。一次关闭是按某个档位那一刻的明文流动性来定它的奖金大小的，
而对账正是把更早一期的结转额变回明文流动性的那一步。
先对账，那笔钱立刻计入奖金大小；后对账，它就得再等一期。

这两件事在同一瞬间变得可做。第 `p` 期的窗口在周期 `p+2` 结束时结束，
而第 `p+2` 期在周期 `p+3` 开始时变得可关闭，所以 keeper 先做终结和任何到期的对账，再做关闭。

顺序错了不会丢任何东西，但错在哪一边是有讲究的。
先关闭再终结，那个档位的结转额还没有处于待对账状态，所以 `openDraw` 会把它折进这次报价，
那笔钱仍然可以被赢走；它只是不会抬高公布的奖金金额，因为 `closeDraw` 只按明文流动性来定那个数。
而如果是终结、关闭、再对账，那个结转额就处于待对账状态：
`openDraw` 会把一笔待对账的结转额整个排除在本期开奖之外，
所以在对账清掉那个标志之前，这笔钱既没被拿出来也赢不到。
在 Sepolia 上每个档位在每次终结时都到期，所以这是常规情形，
这也是为什么 keeper 在做完终结和对账之后、关闭之前，会再读一次那些结转额。
不管哪种情况都不会丢东西：对账之后的第一次关闭会把它们全部折回去。

## keeper 停机时会怎样

什么都不会丢。这就是全部答案，而它成立是因为一个被错过的步骤是这样处理的：

| 被错过的步骤 | 后果 |
| --- | --- |
| 关闭从未发生，或者发生在 `closeDeadline` 之后从而回滚 | 这期开奖停在 `None` 并被跳过。它的流动性从来没被移走过，所以留在档位里，下一期再拿出来发。收割额由下一次关闭收走。 |
| 发奖从未在窗口内发生 | 一次迟到的发奖照样记入收割额、照样把拿出来的流动性退回档位，并把这期标记为 `Skipped`。没有收益和流动性消失。 |
| 遍历没走到每一位储户 | 遍历漏掉的储户从这一期什么都拿不到。他们在这次报价中的那一份会在终结时折进该档位的结转额，并被再次拿出来发。这是唯一一处真实储户会失去某样他本可能赢到的东西的情形，它是局限 2。 |
| 终结或对账迟到了 | 各档位在一段时间里持有更少的明文流动性，所以奖金金额更小。一笔已被终结公布、但还没有对账清掉的结转额，会一直被排除在每一次关闭之外，直到对账落地。没有东西丢失：对账之后的第一次关闭会把它们全部折回去。 |

keeper 卡住会让资金池损失开奖次数，不会损失钱。存款和提取全程照常工作，
因为暂停路径从来碰不到它们，而一期卡住的开奖也不会锁住任何东西。

我们上一版部署就是那个警示例子：`openDraw` 是无需许可的，但没人去调用它，
所以线上那个池子带着一期准备好被开启的开奖坐了 26 小时。
无需许可和自动化不是一回事。这就是为什么这一版设计有一个真正的 keeper，
以及它下面有一条冗余路径。

## 储户怎么自己推进一期开奖

上面每一步都无需许可，而应用把它们全部开放在自己的「跑一次开奖」页面上，
在储户所在池子的 `/app/<slug>/run`，也就是侧栏里标着「任何人」的那一行。
页面顶部有一张卡片写明资金池正在等哪一步，下面五个步骤各自带着自己的按钮，
在没轮到那一步时按钮是灰的，并写明原因：

- **关闭**，然后 **发奖**。关闭定死奖金金额并摇出加密种子。
  发奖在浏览器里取回那四份解密证明，并把签名过的明文发回去。
  那次中继器调用和 keeper 做的是同一个，而 SDK 在页面里完成它。
- **推进。** 为当前开启的那一期跑 `evaluate(p, count)`，把共享的那条遍历往前推一批。
  同一个调用也出现在「我的开奖」上你自己那张开奖卡片里，写作「推进这期开奖」。
  如果 keeper 停了、而遍历还没走到你，就按这个按钮。
  它不让你挑自己，而这正是它的特性所在：因为没人能把自己单独挑出来，
  发出这笔交易说明不了你到底有没有中奖。
- **终结** 和 **对账。** 为任何窗口已经结束的开奖跑那两个收尾步骤。

这些都不需要我们的许可、我们的密钥，也不需要我们的服务器在线。

## Chainlink 自动化，只覆盖关闭那一步

`HearthPrizePool` 为关闭那一步实现了 Chainlink 的 `checkUpkeep` 和 `performUpkeep` 接口。
注册一个基于时间的 upkeep，会给这个池一条第二的、独立的按时关闭开奖的途径，
而关闭是那个有截止时间的步骤，所以它是唯一一个值得上保险的。

它只覆盖关闭，别的都不覆盖，原因很简单：关闭是唯一一步不需要链下数据的。
发奖需要一份从 Zama 的中继器取回的解密证明。评估需要反复执行直到一个游标绕回来。
对账需要另一次解密。一个链上自动化网络取不到这里的任何一样，
所以假装它可以就是演戏。

这个 upkeep 是可选的。它需要一个已注册 upkeep 账户里的 LINK，
它是冗余而不是主路径，而且它会是一池一个 upkeep，每一个按那个池自己的时间表跑。
七个池上都还没有注册任何一个，所以现在是这些 keeper 独自在跑这些演示池。

我们在本地声明那两个函数的接口，而不是为了两个选择器就把整个 Chainlink 合约包和它的依赖拉进来。

## 预算

每期开奖的成本，来自实际部署。

| 步骤 | 每期交易笔数 | 每笔 gas |
| --- | --- | --- |
| 关闭 | 1 | `1,422,474` |
| 发奖 | 1 | `435,578` |
| 评估，一整批 4 位 | `floor(savers / 4)`，这里是 1 | `3,417,699` |
| 评估，最后那个不满的批次 | 0 或 1，这里是 1，装着一位储户 | 一位储户 `1,291,192`，每多一位加 `708,836` |
| 终结 | 1 | `509,463` |
| 对账 | 3，一个档位一次，因为每个档位每期都到期 | `459,994` |

在 5 位储户下，那就是每期 `8,456,388` gas，按部署时 Sepolia 的基础费用 1 gwei 算，
大约 `0.0085 ETH`。在一小时周期下那是每天 24 期、`0.2030 ETH`；在一天周期下是 `0.0085 ETH`。

把它乘以七个池，就是六个池每六小时而不是每小时开奖的全部原因。
七个池全都按小时是一天 168 期，大约 `1.43 ETH`，公开水龙头跟不上。
一个小时池加六个六小时池是一天 48 期，大约 `0.41 ETH`。
每个 keeper 账户单独供资，所以一个池的 gas 用光了，只会停掉它自己的开奖。

在 Sepolia 上，一批里多一位储户要花 `708,836` gas，
而一个只装着一位储户的批次要花 `1,291,192`，因为调用的固定部分反正都要付。
以计算单元计，一位储户是 mock 协处理器价目表上的 `3,674,128`，
那也是这个数字唯一可读的地方，因为线上的收据不报计算单元。
批次大小 `4` 就是从那次测量对照 Zama 公布的 Sepolia 上限（
每笔交易 20,000,000 计算单元、其中顺序深度 5,000,000）定出来的。
`evaluate` 接受任意数量，所以万一 Zama 给某个操作重新定价，keeper 不用重新部署就能降到更小的批次。

**keeper 会评估完整条遍历。** 链上没有任何东西限制评估要花多少钱，
而 keeper 也不会中途停下；它强制执行的是一个费用上限
（`KEEPER_MAX_FEE_GWEI`），在这个上限之下它会一直发送直到游标走到末尾。
诚实的后果写在[威胁模型](../security/threat-model.md)里：
一个被无价值地址灌满的池子，让 keeper 每期花更多 gas，而不是让储户丢掉奖金，
因为在该周期之前没有观测点的地址会被跳过，不做任何加密运算。
如果 keeper 停了，任何人都可以按「推进」，而且因为遍历每期从一个不同的点开始，
没有人会永远待在队尾。

## 一池一个 keeper

`packages/keeper/ecosystem.config.cjs` 在 pm2 下启动全部七个，一池一个进程。
一个进程由 `HEARTH_ADDRESSES_FILE` 告知自己驱动哪个池，
那就是那个池的部署所写出的地址文件，它同时也给出代币符号、小数位和用来签名的账户序号。
`KEEPER_NAME` 是每一行日志都带的标签。

| pm2 进程 | `HEARTH_ADDRESSES_FILE` | `KEEPER_ACCOUNT_INDEX` |
| --- | --- | --- |
| `hearth-keeper-usdc` | `hearth.json` | 1 |
| `hearth-keeper-usdt` | `hearth.usdt.json` | 10 |
| `hearth-keeper-weth` | `hearth.weth.json` | 11 |
| `hearth-keeper-bron` | `hearth.bron.json` | 12 |
| `hearth-keeper-zama` | `hearth.zama.json` | 13 |
| `hearth-keeper-tgbp` | `hearth.tgbp.json` | 14 |
| `hearth-keeper-xaut` | `hearth.xaut.json` | 15 |

`usdc` 那个进程指向 `hearth.json` 而不是 `hearth.usdc.json`，
因为那是第一次部署写出的文件，当时池子还没有标识，而正在跑的那个 keeper 已经指着它好些天了。
两个文件里的地址是一样的。

这些序号故意隔开，好让之后加一个池不必重新编号，而且每个账户都需要自己的 Sepolia ETH。
序号 0 是部署者，keeper 会拒绝它。

## 怎么跑它

keeper 是 `@hearth/keeper` 这个包。它用部署所使用的同一句
`RECOVERY_PHRASE` 的某一个账户签名，并从
`packages/contracts/.env` 读取 `SEPOLIA_RPC_URL`；它自己的设置在 `packages/keeper/.env` 里：

```
HEARTH_ADDRESSES_FILE=../contracts/deployments/sepolia/hearth.weth.json
KEEPER_ACCOUNT_INDEX=11            # defaults to the index in the address file
KEEPER_NAME=weth                   # defaults to the slug in the address file
KEEPER_BATCH=4                     # savers of encrypted work per evaluate call
KEEPER_POLL_SECONDS=30
KEEPER_MAX_FEE_GWEI=20             # refuse to send above this
```

```
npm run compile -w @hearth/contracts    # the keeper reads the compiled ABI
npm run build -w @hearth/keeper
npm run plan -w @hearth/keeper          # one pass, simulates every call, sends nothing
npm run once -w @hearth/keeper          # one live pass
pm2 start packages/keeper/ecosystem.config.cjs   # all seven
pm2 logs hearth-keeper-weth                      # one pool
```

`plan` 和 `once` 驱动的是 `HEARTH_ADDRESSES_FILE` 所指的那个池，
所以检查另一个池只需要在命令前面加一个变量。如果 `HEARTH_VAULT` 和
`HEARTH_POOL` 还从单池时代留在 `packages/keeper/.env` 里，
把它们删掉：它们的读取优先于地址文件，那样七个进程会全都去驱动同一个池。

一次轮询每条事实打一行日志，每一行都带着该进程所驱动的那个池的标签，
所以七份交错的日志仍然可读。金额带着那个池自己的符号和自己的小数位，两者都读自地址文件：

```
09:14:37 [usdc] closed draw 41 (gas 1,422,474)
09:14:39 [usdc] draw 41: asking the relayer for the seed, the scale, the empty flag and the harvest
09:14:53 [usdc] awarded draw 41: 3 tiers, prizes 12.40 / 2.10 / 0.40 cUSDC, harvest 3.60 cUSDC (gas 435,578)
09:15:07 [usdc] evaluated draw 41: 4 of 9 savers done (gas 3,417,699)
09:15:38 [usdc] nothing to do: period 43, draw 41 has 8 of 9 savers evaluated
```

WETH 那个进程在 `[weth]` 下打印同样的行，用的是 `cWETH`。每一类日志行的含义，逐行的说明，
在 keeper 包自己的 README 里，`packages/keeper/README.md`。

keeper 在两次轮询之间是无状态的：它从链上读开奖状态、评估游标和对账节奏，然后算出该做什么。
重启它不会丢任何东西。每个池只跑一个实例，而且绝不要在一个账户上跑两个：
在链上，每一步每期每档位恰好只能成功一次，两次 evaluate 调用也只是推进同一个游标，
但同一个账户上的两个 keeper 会为交易 nonce 互相抢。

## 本页没有覆盖什么

它没有讲 keeper 的那些交易到底对钱做了什么，那是
[一次开奖是怎么进行的](../concepts/how-a-draw-works.md)。它没有讲部署，那是
[部署](deploying.md)。它也不做任何可用性承诺：我们跑一个 keeper，但我们不为它做保证，
而这套设计正是为了让「不做保证」这件事可以接受而建的。

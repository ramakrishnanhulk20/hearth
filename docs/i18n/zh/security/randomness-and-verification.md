# 随机性与可验证性

一期开奖只有在陌生人能核查它的时候才有价值。本页讲的就是怎么核查。

## 种子从哪来

一次调用，在关闭一期开奖的那笔交易内部：

```solidity
euint64 seed = FHE.randEuint64();
```

它在 Zama 的协处理器内部运行。这个数由一个密码学安全的生成器在网络 FHE 密钥之下产出，
而返回给合约的是一个密文句柄，不是一个数字。那一刻没有任何人见过这个值：
调用者没有，我们没有，出块者也没有。

Zama 生成器的两个性质在这里很要紧，而且两个都写在 Zama 自己的文档里：

- **它必须在一笔交易内部运行。** 生成一个随机值会改变链上生成器的状态，
  所以它没法通过 `eth_call`（那种只读的调用模拟方式）来做。
  没有人能在链下预演一期开奖，看看自己会不会中。
- **它是密码学安全的，并且保持加密**，直到有什么东西明确地把它变成可解密。

## 为什么没人能重摇它，或者改变它能赢到多少

四件事，合在一起。

1. **关闭只能成功一次。** 开奖的状态机允许 `closeDraw(p)` 每期恰好执行一次。
   不存在第二次尝试去买一个更好的数字。
2. **它被摇出来的时候值是未知的。** 既然种子在创建时就是密文，
   发出那笔关闭交易的人不会因为发过它而学到任何东西。争着当调用者毫无意义。
3. **公布这一步是单向的。** 关闭之后，种子被标记为可公开解密。
   那个标志在 Zama 的访问控制列表上是永久且不可撤销的，
   所以世界看到的那个数字，就是合约当初承诺的那个数字，不是事后挑的。
4. **奖金在种子存在之前就定死了。** 每个档位的奖金金额和它拿出的流动性，
   都在同一笔关闭交易的开头算出来，在 `randEuint64` 被调用之前。
   在更早的一个草案里，它们是在后面的发奖时才设定的，
   这就留下了一个窗口，有人可以在里面读到种子、算出自己中了、
   然后在档位之间挪动流动性把那次中奖做得更值钱。那个窗口没有了。

拿它和其他方案对比一下。一期由区块哈希驱动的开奖，可以被一个不喜欢结果的验证者重摇。
一期由链下数字驱动的开奖，可以被直接挑选。这里两者都不可能，
而这正是随机数要在链上、在加密之下生成，而绝不由一个链下生成器产出的全部原因。

## 什么会变公开，什么时候

| 数值 | 何时公布 | 为什么它必须公开 |
| --- | --- | --- |
| 种子 `R` | 关闭时，中继器解密之后可读 | 没有它，没人能重算一个阈值 |
| 规模计数，由它推出区间 `M` | 关闭时 | 阈值是相对池子规模的 |
| 该周期是否非空 | 关闭时 | 区分一期空开奖和一期真开奖 |
| 该期的收割额 | 关闭时 | 它是供给后续奖金的那笔钱 |
| 每个档位的奖金金额和它拿出的明文流动性 | 关闭时 | 核查一次中奖能拿多少所必需 |
| 每个档位的结转额 | 每一期的终结时，因为每个档位每期都对账 | 核查该档位派出了多少份奖所必需 |
| 未足额计数器 | 终结时 | 证明资金池为金库写下的每一笔入账都出了钱 |

有两样东西被刻意 **排除** 在那份清单之外。资金池精确的时间加权余额总额从不公布，
因为公布它会让观察者精确还原一个孤单动钱者的存款额；公布的是它上方的那个区间。
另外，任何针对单个储户的数值都从不会被标记为可公开解密。

清单上的每一样，都在它所决定的那个周期已经结束之后才到来。
公布 `R` 帮不了任何人去改变一个权重，因为周期 `p` 的权重在周期 `p` 结束的那一刻就冻结了，
而那是在这期开奖还没法被关闭之前。

那些数字每一个抵达合约时都带着 Zama 密钥管理服务的签名，
由 `FHE.checkSignatures` 在链上验证。证明按固定顺序与句柄绑定：
发奖时是 `[seed, scaleCount, nonEmpty, harvested]`，对账时是一个结转额句柄。
没有东西能在这些位置之间被打乱，也不能被重放到另一期开奖上。
开奖的状态机就是重放防护：每一步每期只能成功一次，而对账每个档位只能成功一次。

## 区间，以及金库怎么追踪它

资金池在某周期的时间加权余额总额 `W` 保持加密。开奖实际针对的数字是 `M = 2^m`，
刚好不小于 `W` 的那个 2 的幂。

金库是一期一期地追踪 `m`，而不是每次从头算。每次关闭时，
它在加密状态下把 `W` 与上一期 `m` 周围的五个 2 的幂做比较，
把这五个结果加成一个加密的小计数，并把那个计数标记为可公开解密。
资金池读取验证过的计数并算出新的 `m`，它每期最多移动三步。
另外一次与 1 的加密比较给出非空标志。

所以每期的公开记录是一个小整数，而且只有在池子跨过某个 2 的幂时它才会变。
资金池上的 `scaleBits()` 读出当前的 `m`；部署时用 `initialScaleBits` 给它一个初值，
也就是第一个周期总额的预期比特长度，之后追踪器每期最多纠正三个比特的误差。

## 任何人怎么重算一个阈值

下面用到的全是公开数据。不需要钱包，不需要签名，不需要许可。

对第 `p` 期开奖、储户地址 `u`、有 `count[t]` 份奖且概率为
`oddsNum[t] / oddsDen[t]` 的档位 `t`：

```
prn         = keccak256(abi.encode(R, p, u, t))
r           = prn mod M                                        // 0 <= r < M
threshold_k = floor((r + k * M) * oddsDen[t] / (oddsNum[t] * count[t]))
```

对每一个从 `0` 到 `count[t] - 1` 的 `k`。当且仅当那位储户在周期 `p` 的时间加权权重
严格大于 `threshold_k` 时，他中了第 `k` 份奖。

你不必自己重新实现它。金库把
`thresholdOf(drawId, saver, tier, k)` 开放成一个纯视图函数，用的就是评估所用的那套算术，
所以应用的验证面板、测试套件，以及任何拿着区块浏览器的人，读的都是同一份实现。
如果你更愿意拿自己的代码去核对合约，在链下重新实现它是四行大整数算术。

一个小数字的完整算例在
[中奖判定](../concepts/winner-selection.md)里。这里是一个填好的例子，
取自 Sepolia 上一期真实开奖，来自 `usdc` 池，它的奖池合约是
`0xA0785AacF30B6FE46EDc53CD8A9db1d94FeF5Df2`。每个池为它自己的开奖公布同样的字段：

| 字段 | 值 |
| --- | --- |
| 开奖期 | `2, the period from 23:00 to 00:00 UTC on 2 September 2026` |
| 种子 `R` | `5625525180683981523` |
| 区间 `M` | `2^43, which is 8,796,093,022,208 balance-seconds` |
| 收割额 | `19.531380 USDC` |
| 各档位奖金金额 | `3.559644 / 1.779822 / 0.889911 USDC, grand / mid / frequent` |
| 各档位派出的奖项数 | `0 / 0 / 5, against a funded capacity of 2 / 2 / 8` |

从链上读出：种子和区间来自资金池的 `DrawAwarded` 事件，
奖金金额和拿出的流动性来自 `drawParams(2)`，派出的奖项数来自该期的三条
`TierReconciled` 事件，因为一个档位拿出来但没派出去的部分，恰好就是它公布的结转额。
大奖档和中档在这一期什么都没派，把拿出来的全部交了回去，
这正是一个 24 分之 1 和一个 6 分之 1 的档位大多数时候会做的事。

应用的验证面板在浏览器里为你输入的任何地址做这套算术，
在你想看的那个池子的 `/verify?pool=<slug>` 上。它没有任何特权访问；
它用的是同样的公开输入和同样的公式。

## 为什么取余没有偏差

把一个大随机数用普通取余压进一个范围，通常是有偏的。如果 `2^256` 不是那个范围的整数倍，
低位余数出现得会稍微频繁一点，而那份偏差会不均匀地落在储户身上。
PoolTogether V5 用拒绝采样解决它，Hearth 更早的一个草案也是。

Hearth 不再需要了。`M` 按构造就是 2 的幂，而 `2^256` 是每一个不超过 `2^256` 的 2 的幂的整数倍。
所以 `prn mod M` 只是一个 256 位哈希的低 `m` 位，
从 `0` 到 `M - 1` 的每一个值都来自同样多的输入。**偏差是零，不是很小**，
没有循环，没有拒绝，也没有什么需要验证者小心复现的东西。

这是公布区间而不是公布精确总额带来的一个副产品，
值得说一句，因为它去掉了一段任何核查开奖的人本来都得精确对上的代码。

## 地址研磨没有用

一旦 `R` 公开，有人可能不断生成地址，直到找到一个阈值很低的。那会毫无用处。
阈值是拿来和周期 `p` 的权重比较的，而一个全新地址在周期 `p` 或之前没有任何观测点，
所以它的权重是零。零超不过任何阈值。要在周期 `p` 有权重，
你就得在周期 `p` 期间持有过余额，而那个周期在 `R` 存在之前就结束了。

为未来的某一期研磨则因为另一个原因失败：那一期的种子还没生成，而且它不可预测。

## 验证证明了什么，没有证明什么

把这件事说精确，就是本页的意义。

**它证明：**

- 种子是在链上、在一笔交易内部、在网络密钥之下生成的，并且恰好公布过一次。
- 奖金金额和拿出的流动性是在那个种子存在之前定死的。
- 应用到每位储户身上的规则是公开的、统一的，而且任何人都能重算。
- 奖金金额由档位流动性和档位参数经公开算术推出。
- 每个档位派出的奖项数，与它拿出的金额减去它结转额里回来的部分对得上。
- 资金池为金库写下的每一笔入账都出了钱，因为未足额计数器被公布出来而且是零。

**它没有证明：**

- 协处理器的生成器是均匀的。那是 Zama 的引擎，它是被信任的，而不是在这里被验证的。
- 密钥管理服务签的是种子句柄的真实明文。合约检查的是签名，不是语义。
  一个不诚实的法定人数组可以签一个自己挑的值。这套协议上的每一个应用都共享这条假设；
  它是[威胁模型](threat-model.md)里的攻击者 8。
- 公布的区间真的是所有储户权重之和的区间。外人加不起加密权重，现在也看不到那个和。
  他们手里有的，是同样公开且不可变的代码从同样的观测点算出了那些比较和每位储户的权重，
  以及那些守恒不变式成立：已付等于已记入，而且没有人提取超过本金加中奖余额。
- 关于谁中了奖的任何事。那正是全部要义所在，
  也是为什么公布得更多会让验证更强、让产品更差。公布精确总额就是那个具体例子：
  它让池子的规模可核查，同时也让一个孤单动钱者的存款额可以还原到基础单位。

## 一位储户能核查什么，别人不能

一位储户可以比外人多走一步，因为他能解密自己在某一期的权重和入账额。

1. 揭示你在第 `p` 期的权重。
2. 从公开的 `R` 和 `M` 重算你自己的阈值，或者从
   `thresholdOf` 读出来。
3. 数一数你超过了几个，乘以该档位的奖金金额。
4. 揭示你在第 `p` 期的入账额，核对它对不对得上。

如果对不上，要么是某个档位在遍历走到你之前就耗尽了，那是有据可查的取小，
要么就是有什么地方出了问题，而你手里有数字可以证明。应用会替你做完这四步，并把算术展示出来。

# 中奖判定

这是整个产品的核心：在没人读得懂的数字上判定谁中了奖，而且判定方式仍然让陌生人可以核查。

**要紧的一句话是：中奖判定在开奖那一刻就定死了，评估只是把它写下来。**
资金池验证随机种子和池子总额所落入区间的那一刻，每位储户在每个档位的结果就已经确定了。
阈值是任何人都能重算的公开数字，而被拿来比较的加密权重再也不会改变。
评估是记账。它没法被引导、被抢跑，也没法用某种方式跳过而改变谁中了奖。

## 一期开奖发奖时，什么被定死了

| 符号 | 是什么 | 公开吗？ |
| --- | --- | --- |
| `R` | 本期的随机种子 | 是，周期结束之后 |
| `M` | 池子总权重所落入的区间，一个 2 的幂 | 是，周期结束之后 |
| `prize[t]` | 档位 `t` 里一份奖付多少 | 是，关闭时定死 |
| `offered[t]` | 档位 `t` 为本期拿出的流动性 | 是，关闭时定死 |
| `count[t]` | 档位 `t` 每期提供多少份奖 | 是，部署时定死 |
| `odds[t]` | 档位 `t` 多久触发一次，以分数表示 | 是，部署时定死 |
| `W` | 资金池在该周期的时间加权余额总额 | **否。从不公布** |
| `twab` | 某一位储户在该周期的时间加权余额 | 否，加密，仅该储户可读 |

最后两行是秘密。`twab` 是每个人各自的。`W` 是所有 `twab` 的和，
之所以不公布，是因为精确公布它就等于把一个孤单动钱者的存款额，通过减法交到观察者手里。
开奖实际针对的是 `M`：刚好不小于 `W` 的那个 2 的幂。
所以 `M` 落在 `W` 和 `2W` 之间，而观察者从这一期到下一期唯一能学到的，是池子有没有跨过某个 2 的幂。

## PoolTogether 的规则，和我们的

PoolTogether V5 在档位 `t` 里给每位储户 `count[t]` 次独立机会。
每次机会以 `min(1, twab * odds[t] / W)` 的概率中奖。
所以一位储户在某档位的期望中奖数，是他在池中的占比，乘以该档位的概率，再乘以奖项数量。

在加密数字上照字面做这件事，意味着要为每位储户的每份奖摇一个新随机数，而且还需要精确的 `W`。
Hearth 用「每位储户每档位一个均匀随机数」加上「一梯嵌套阈值」，并用 `M` 代替 `W`，复现了同样的形状。

写 `z = twab * odds[t] * count[t] / M`。那就是这位储户在这个档位的期望中奖数。
Hearth 付给他们 `floor(z)` 或 `ceil(z)` 份奖，上限为 `count[t]`，而多期下来的平均值恰好是 `z`。

因为分母是 `M` 而不是 `W`，每位储户的期望都被乘上了 `W / M`，一个介于二分之一和一之间的数。
把所有储户加起来，一个档位每期派出的是它名义 `count * odds` 份奖的一半到全部之间。
这里没有任何东西损失。一个档位没派出去的部分留在它的加密结转额里，下一次关闭时再拿出来发，
所以长期来看所有收益仍然会发出去；只不过奖金金额会稳定在更高的水平。见
[奖金与档位](prizes-and-tiers.md)。

## 判定式，逐步拆解

对于第 `p` 期开奖里档位 `t` 中的储户 `u`：

1. 推导他在这个档位的随机数。`prn = keccak256(R, p, u, t)`。
   因为储户地址和档位序号都进了哈希，每位储户都得到自己的数字，每个档位得到不同的数字，
   而这些全都来自那一个种子 `R`。
2. 把它压进区间。`r = prn mod M`，一个从 `0` 到 `M - 1` 的整数。`M` 是 2 的幂，
   所以这只是一个 256 位哈希对 2 的幂取余，结果恰好均匀，不需要纠偏。
   这是公开值上的公开算术。
3. 搭起梯子。对每份奖 `k`，从 `0` 到 `count[t] - 1`：
   `threshold_k = floor((r + k * M) * oddsDen[t] / (oddsNum[t] * count[t]))`。
   这些是公开数字。任何人都能为任何地址算出它们，而且合约把同一套算术开放成了视图函数
   `thresholdOf(drawId, saver, tier, k)`，所以应用的验证面板、测试和任何外部核查者用的都是同一份实现。
4. 比较。当储户的加密权重大于 `threshold_k` 时，第 `k` 份奖中了。
   这是唯一一个碰到秘密的步骤，它是一次加密比较，结果是一个没人读得懂的加密真或假。
5. 支付。每中一份奖，就给该储户在这个档位的加密支付额加上 `prize[t]`，
   用的是加密选择而不是 if 语句，所以无论他们一份没中还是全中，交易看起来都一模一样。
6. 取小。该档位付给这位储户的金额，取「他们中到的」和「该档位还剩下的」中较小的那个。
   这次减法会更新该档位的加密剩余流动性。
7. 入账。取小之后的金额被加到该储户的加密中奖余额上。

阈值随 `k` 递增，所以一位储户会中第 `0` 到第 `j-1` 份奖，然后就停下。
第 `k` 份奖的条件恰好是
`twab * odds * count > r + k * M`。

### 唯一一处明文分支

如果某个阈值大于 `2^64 - 1`，那么任何 64 位权重都不可能超过它，
所以答案是假，比较被整个跳过。当 `M` 非常大时，低概率档位会出现这种情况。
既然阈值只随 `k` 递增，该档位的循环就在第一个这样的阈值处停下，而不去检查剩下的。
这个分支是在一个公开数字上做的。Hearth 里没有任何地方在秘密上分支。

## 完整算例：三位储户，一个档位

一个很小的池子，好让数字保持可读。一个档位：高频档，`count = 4`，
`odds = 1`（也就是 `oddsNum = 1`，`oddsDen = 1`）。
权重以该池所持代币的余额秒计；本例把它们当作 USDC 来读。

| 储户 | 权重 | 占 `W` 的比例 | `z = weight * 4 / M` |
| --- | --- | --- | --- |
| Ada | 600 | 60% | 2.34 |
| Ben | 300 | 30% | 1.17 |
| Cy | 100 | 10% | 0.39 |
| **总计 `W`** | **1,000** | 100% | **3.91** |

`W` 是 1,000，所以区间是 `M = 1,024`，刚好不小于它的那个 2 的幂。
池子外面的人看不到那个 1,000。他们看到的是 1,024。

注意总计那一列。该档位的名义派奖是 `count * odds = 4` 份每期。
它实际期望派出的是 `4 * W / M = 4 * 1000 / 1024 = 3.91`。那就是 `W / M` 缩放，
在这里是 2.3% 的折扣，因为 1,000 靠近它所在区间的上沿。
一个总额 520 的池子会落在同一区间的下沿，该档位期望派出的就大约是 2.03 份。

现在开奖发生了。每位储户的 `r` 来自把种子和他们自己的地址一起哈希，
所以对每个人都是不同的数字，落在 0 到 1,023 之间。

**Ada，`r = 271`。** 阈值是 `floor((271 + k * 1024) / 4)`：

| k | 阈值 | Ada 的权重 600 超过了吗？ |
| --- | --- | --- |
| 0 | 67 | 是 |
| 1 | 323 | 是 |
| 2 | 579 | 是 |
| 3 | 835 | 否 |

Ada 中了 3 份奖。她的期望是 2.34，所以 3 是 `floor` 或 `ceil` 中偏高的那一侧。

**Ben，`r = 812`。** 阈值 `floor((812 + k * 1024) / 4)`：

| k | 阈值 | Ben 的权重 300 超过了吗？ |
| --- | --- | --- |
| 0 | 203 | 是 |
| 1 | 459 | 否 |

Ben 中了 1 份奖，期望是 1.17。

**Cy，`r = 155`。** 阈值 `floor((155 + k * 1024) / 4)`：

| k | 阈值 | Cy 的权重 100 超过了吗？ |
| --- | --- | --- |
| 0 | 38 | 是 |
| 1 | 294 | 否 |

Cy 中了 1 份奖。他的期望是 0.39，所以今天算他走运。
多期下来，他大约 39% 的时候中一份奖，其余时候什么都没有。

期望 3.91 份，实际派出了五份。这没问题：每份奖是该档位流动性的八分之一，
所以在耗尽之前它能付出八份。见[超额派奖](prizes-and-tiers.md)。

现在看看这一切结束后观察者看到了什么。上面三张表他们自己都能算出来，
因为 `R`、`M`、阈值和地址都是公开的。他们做不到的是填上右边那一列，因为权重是加密的；
他们也还原不出那个 1,000，因为公布的只有 1,024。
等该档位在一期之后对账，他们会知道它派出了多少份奖。但他们永远不会知道派给了谁。

## 为什么把钱拆到多个钱包毫无收益

这是一个做砸了的版本会丢掉的性质。

一位储户在某档位的期望中奖数是 `z = twab * odds * count / M`，它对权重是线性的，
而 `M` 不取决于池子的权重是怎么在各地址之间划分的。
把 600 的权重拆成两个 300 的钱包，每个得到 `z = 1.17`，合计 2.34。完全一样。
拆成六个 100 的钱包，每个得到 0.39，合计 2.34。还是完全一样。
这里没有阈值可以博弈，也没有舍入可以套利，只有更多的 gas 要付。

这个设计的早期版本把奖项数量折进了一个更宽的单一中奖区间，
使得每位储户在每个档位最多只能中一份奖。那把大额持有者压到了他们应得份额之下，
反而给拆分账户的人发钱。一次设计评审发现了它，嵌套梯子取而代之。

## 它的开销

每位储户每期的加密工作量是：一次乘法和一次加法算出权重，
然后对每个档位，每份奖一次比较和一次选择，外加一次取小。
在 Sepolia 的三个档位下，那就是 6 次比较、6 次选择，以及大约十来次加、减和取最小值。

Zama 公布的 Sepolia 单笔交易预算是总共 20,000,000 计算单元，其中顺序深度 5,000,000，
定价上一次 64 位加法 162,000，一次比较约 118,000，一次选择 55,000，
一次乘以公开数字 365,000。这些数字把一位储户放在了几百万计算单元这个量级，
这就是评估要按每笔交易 `4` 位储户分批的原因。实测数字是
`3,674,128 on the mock coprocessor's price table (the live coprocessor does not report compute units in a receipt)` 每位储户，实测 gas 是 `708,836 (the marginal cost of one more saver in a batch; a batch of one costs 1,291,192)`。

## 本页没有覆盖什么

它没有讲 `R` 从哪来、或者怎么验证它，那是
[随机性与可验证性](../security/randomness-and-verification.md)。它没有讲
`prize[t]` 是怎么定大小的、或者一个档位在开奖中途耗尽时会怎样，那是
[奖金与档位](prizes-and-tiers.md)。它也不宣称隐藏了谁参与了：
储户名单、评估批次和每档位的中奖数量全都是公开的。见
[什么保持私密](../security/what-stays-private.md)。

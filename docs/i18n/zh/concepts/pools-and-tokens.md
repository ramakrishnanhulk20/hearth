# 资金池与代币

Hearth 不是一个池。它是七个，Zama 的 Sepolia 地址表上每种机密代币一个，
每一个都有自己的 `HearthVault`、自己的 `HearthPrizePool` 和自己的 `SponsoredYieldSource`，
有自己的储户、自己的奖金和自己的 keeper。

这些合约是同一套代码，用不同的构造函数参数部署了七次。链上不共享任何东西：
没有注册表，没有路由器，没有共享余额。WETH 池里的储户看不到、碰不到 USDC 池，也不会被它碰到，
而某一种代币上暂停的金库或卡住的 keeper，不影响其余六个继续运行。

## 为什么是六小时，而不是七个全都一小时

因为 gas。一个五位储户的池子开一次奖，按 Sepolia 上实际收据测得是 `8,456,388` gas：
一次关闭、一次发奖、两批评估、一次终结，外加每个档位一次对账。按 1 gwei 算就是 `0.0085 ETH`。
七个池全都每小时开奖，一天就是 168 次开奖，大约 `1.43 ETH`，
公开水龙头根本没法在整个评审窗口里把它喂饱。一个十位储户的池子一次开奖是 `12,582,923` gas，
账单还会随之增长。

所以后部署的那六个池每六小时开一次奖。那是每池每天四次，
七个池加起来一天大约 `0.41 ETH`，而不是 `1.43`，而每天四次也仍然频繁到访客一次访问就能看到一期落地。
USDC 池保留它的小时时钟，以及随之而来的那些历史开奖记录。

中奖概率是按各池自己的周期设定的，而不是照搬，所以产品的手感在两种时钟上是一样的：

| 档位 | 小时池（`usdc`） | 六小时池 |
| --- | --- | --- |
| 大奖档 | 数量 1，概率 24 分之 1，份额 40 | 数量 1，概率 4 分之 1，份额 40 |
| 中档 | 数量 1，概率 6 分之 1，份额 20 | 数量 1，概率 2 分之 1，份额 20 |
| 高频档 | 数量 4，概率 1 分之 1，份额 40 | 数量 4，概率 1 分之 1，份额 40 |

因此每个池的大奖大约每天派出一次。中档是两种时钟唯一有差别的地方：
小时池上每天约四次，六小时池上每天约两次，因为把概率减半并不足以补偿开奖次数只剩六分之一。
每个池的每个档位都每期对账，原因见
[奖金与档位](prizes-and-tiers.md)。

## 小数位，以及一个金额意味着什么

Zama 的 Sepolia 地址表上每一个机密包装合约都读作六位小数，无论底下的公开代币是多少位，
因为包装合约把自己封顶在六位，并把差额算进它的 `rate()`。
Confidential WETH 是最清楚的例子：它的底层是 18 位小数，所以包装合约的 `rate()` 是一万亿，
包装合约的一个基础单位等于公开代币的一万亿个基础单位。

`packages/contracts/hearth.config.ts` 里的每一个金额都以包装合约的基础单位计，
而部署脚本和各项任务在接触公开代币之前，会先乘上它们从链上读到的比例。这不是细节。
我们自己的审计发现过一个 bug：某个池记入的是调用方传进来的金额，而不是包装合约实际铸出的金额，
在一种 18 位小数的代币上，这会把奖金放大一万亿倍。见
[收益来源](yield-source.md)。

## 每个池初始注入了什么

`hearth:seed --token <slug>` 会赞助收益来源，并放进五位演示储户，用账户序号 2 到 6，
好让第一位访客落在一个已经有人的池子里。各代币的注资额不同，因为一个池得看起来像它所持有的资产：
1,200 枚美元稳定币和 0.6 个以太是同一个量级的储户。

| 池 | 五位演示储户的注资额 | 赞助额 | 释放的奖金 |
| --- | --- | --- | --- |
| `usdc` | 1,200 / 600 / 300 / 150 / 75 | 10,000 USDC | 每小时 20 USDC，即每期 19.998 |
| `usdt` | 1,200 / 600 / 300 / 150 / 75 | 10,000 USDT | 每小时 20 USDT，即每期 119.98 |
| `weth` | 0.6 / 0.3 / 0.15 / 0.075 / 0.04 | 5 WETH | 每小时 0.01 WETH，向下取整为每期 0.0432 |
| `bron` | 2,000 / 1,000 / 500 / 250 / 125 | 15,000 BRON | 每小时 30 BRON，即每期 179.99 |
| `zama` | 2,000 / 1,000 / 500 / 250 / 125 | 15,000 ZAMA | 每小时 30 ZAMA，即每期 179.99 |
| `tgbp` | 1,000 / 500 / 250 / 125 / 60 | 8,000 tGBP | 每小时 16 tGBP，即每期 95.99 |
| `xaut` | 0.4 / 0.2 / 0.1 / 0.05 / 0.025 | 3 XAUt | 每小时 0.006 XAUt，向下取整为每期 0.0216 |

一个来源的速率是每秒整数个基础单位，所以最小的两个速率被向下取整了：
每小时 0.01 WETH 是每秒 2.77 个基础单位，实际释放 2 个；每小时 0.006 XAUt 是 1.67，实际释放 1 个。
每笔赞助的规模都够撑八十期以上，也就是二十天以上，
所以评审窗口期间没有人需要给任何一个池补钱。

## Hearth 拒绝的那种代币

Zama 在 Sepolia 上还发布了一种非 mock 的 **Confidential tGBP**，地址是
`0x167DC962808B32CFFFc7e14B5018c0bE06A3A208`，对应公开代币
`0xf6Ef9ADB61A48E29E36bc873070A46A3D2667ff3`。它的底层铸造权仅限发行方，
所以除发行方之外没人能拿到那个公开代币，没人能把它包装成机密代币，也就根本不可能在它上面开池。

Hearth 还是把它列进了池子选择器，灰掉，原因就写在它名字下面。
部署文件里这条原因只用英文写了一次，写作 `mint restricted to the issuer`，
而应用会用读者正在读的那种语言把它打出来。
选中它会打开一个页面，写明这是什么代币、把两个合约都链到 Etherscan、
说明这是谁施加的限制，并且不提供任何钱包操作，因为一个点下去就回滚的存入按钮比没有按钮更糟。

把这个代币从清单里拿掉会更省事，但看起来就像 Hearth 只是还没顾上它。
一位去找 tGBP 的储户会看到两个条目：能用的那个 mock 池，和不能用的那个官方代币，还有原因。

## 那一排池子显示的是什么

落地页的结尾是一排全部的池子，每一格带着那个池此刻的大奖，在服务端用一次 multicall 读出来，
随页面一起送出，所以故事滚完的时候这一排已经填好了。控制台里的选择器显示同样的数字，
照的是同样的规则。

其中两条规则之所以存在，是因为一个数字可能会骗人：

- 一个读取没有回来的池显示 `未读取`，绝不显示 `0.00`。
  一旦写下一个零，一个没应答的节点和一个空奖池看起来就一模一样。
- 一个还没有关闭过第一期开奖的池，在那一排上和选择器里它的名字下面，
  显示的是 **首次开奖 HH:MM UTC** 而不是一个金额。奖金要等第一期开奖派奖之后才会进到各档位，
  所以在那次关闭之前，诚实的答案是一个时间，不是 `0.00`。一格显示哪一种，
  由 `lastClosedDraw` 是否仍然读为零决定；而那个时间本身是 `firstPeriodAt` 加上 `periodLength`，
  也就是第一个周期的结束，也是第 1 期开奖最早能关闭的时刻。
  在每一种语言里，这个时钟都是二十四小时制的 UTC。

## 应用从哪拿到这些地址

应用里从来没有手打的地址。`packages/web/src/lib/chain/pools.json` 里每一个开放的池，
都是从部署脚本写出的文件生成的，用的是：

```
node scripts/sync-pools.mjs        # from packages/web
```

那个脚本读取 `packages/contracts/deployments/sepolia/hearth.<slug>.json`，
拒绝任何缺地址的文件，拒绝两个池声称同一个标识，
并在末尾追加那唯一一条没有部署记录的受限条目。每次部署之后都要跑它。
过去用来存放单个池三个地址的那些环境变量已经没有了。

一位储户正在看哪个池，写在 `/app` 之后的第一段里：

| 路由 | 显示什么 |
| --- | --- |
| `/app` | 跳转到该储户上次用过的池，首次访问则是 `usdc` |
| `/app/<slug>` | 那个池的仪表盘 |
| `/app/<slug>/deposit` | 该代币的铸造、封装和存入 |
| `/app/<slug>/withdraw` | 该代币的提取和解封装 |
| `/app/<slug>/draws` | 该池的历次开奖，以及储户自己在每期中的结果 |
| `/app/<slug>/run` | 该池那五个无需许可的开奖步骤 |
| `/verify?pool=<slug>` | 该池公开的种子、区间和阈值 |

除英文外，每种语言都会在上面所有路由前面加一个语言代码，
所以日文读者的仪表盘是 `/ja/app/weth`。

## 一池一个 keeper

七个池意味着七个 keeper 进程，每一个都用同一句助记词下自己那个账户序号来签名，
因为同一个账户上的两个进程会争抢同一个 nonce。
对照表和 pm2 配置文件在 [keeper](../operations/keeper.md) 里。

# 乱数と検証

抽選は、第三者が確かめられて初めて価値を持ちます。このページはその方法です。

## シードの出どころ

抽選をクローズするトランザクションの中で、呼び出しは 1 回です。

```solidity
euint64 seed = FHE.randEuint64();
```

これは Zama のコプロセッサの内部で実行されます。数値は暗号学的に安全なジェネレータによってネットワークの FHE 鍵のもとで
生成され、コントラクトに返るのは数値ではなく暗号文ハンドルです。その瞬間にその値を見た者はいません。呼び出した人も、
私たちも、ブロックを作った人もです。

ここで効いてくる Zama のジェネレータの性質は 2 つあり、どちらも Zama 自身のドキュメントに書かれています。

- **トランザクションの内部で実行しなければなりません。** 乱数の生成はチェーン上のジェネレータの状態を変えるので、呼び出しを
  読み取り専用でシミュレートする `eth_call` では実行できません。自分が当たるかを確かめるために、抽選をオフチェーンで先読み
  することは誰にもできません。
- **暗号学的に安全であり、暗号化されたままです。** 何かが明示的に復号可能にするまでは、そのままです。

## 誰も引き直せず、当選額も変えられない理由

4 つのことが組み合わさっています。

1. **クローズは 1 回しか成功しません。** 抽選の状態機械は `closeDraw(p)` を抽選ごとにちょうど 1 回だけ許します。より良い
   数値を買うための 2 度目の試みはありません。
2. **引かれた時点で値は不明です。** シードは生成時点で暗号文なので、クローズのトランザクションを送った人がそれによって
   何かを知ることはありません。呼び出し役を争う意味がありません。
3. **公開のステップは一方向です。** クローズのあと、シードは公開復号可能と印を付けられます。そのフラグは Zama のアクセス
   制御リスト上で恒久的かつ取り消し不能なので、世界が見る数値は、コントラクトがコミットした数値であって、あとから選ばれた
   数値ではありません。
4. **賞はシードが存在する前に確定します。** 各ティアの賞の金額と差し出す流動性は、同じクローズのトランザクションの冒頭、
   `randEuint64` が呼ばれる前に計算されます。初期の草案ではこれが後の授与の時点で設定されており、誰かがシードを読み、自分が
   当たったと分かってから、ティア間で流動性を動かして当選額を大きくできる余地が残っていました。その余地はなくなりました。

代替の設計と比べてみてください。ブロックハッシュを使う抽選は、結果が気に入らないバリデータが引き直せます。オフチェーンの
数値を使う抽選は、そのまま選べます。ここではどちらも不可能です。それこそが、乱数をオフチェーンのジェネレータではなく、暗号化の
もとチェーン上で生成している理由です。

## 何が、いつ公開されるか

| 値 | いつ公開されるか | なぜ公開でなければならないか |
| --- | --- | --- |
| シード `R` | クローズ時、リレイヤーが復号したあとに読めます | これがなければ誰もしきい値を再計算できません |
| スケールカウント、そこから区分 `M` が決まります | クローズ時 | しきい値はプールの規模に対する相対値だからです |
| その期間が非空だったかどうか | クローズ時 | 空の抽選と本物の抽選を区別します |
| その抽選のハーベスト | クローズ時 | 後の賞金を賄うお金だからです |
| 各ティアの賞の金額と、差し出した平文の流動性 | クローズ時 | 当選が何を支払うかを確かめるのに必要です |
| 各ティアの繰越額 | 毎回の抽選のファイナライズ時。どのティアも毎回の抽選で精算するからです | そのティアが何件支払ったかを確かめるのに必要です |
| 未充当カウンタ | ファイナライズ時 | ボールトが書いたすべての付与にプールが資金を出したことを証明します |

意図的にこの一覧に**入っていない**ものが 2 つあります。プールの正確な合計時間加重残高は決して公開されません。それをすると、
単独でお金を動かした人の預入額を観察者が正確に復元できたからです。代わりにその上にある区分を公開します。そして預入者ごとの
値が公開復号可能と印を付けられることはありません。

一覧のすべては、それが決める期間がすでに終わったあとに届きます。`R` を公開してもウェイトを変える助けにはなりません。期間 `p`
のウェイトは期間 `p` が終わった瞬間に凍結され、それは抽選をクローズできるようになるより前だからです。

この数値はどれも、Zama の鍵管理サービスの署名を伴ってコントラクトに届き、`FHE.checkSignatures` がチェーン上で検証します。
証明はハンドルに固定の順序で紐付いています。授与では `[seed, scaleCount, nonEmpty, harvested]`、精算ではティアごとに繰越額の
ハンドル 1 つです。枠の間で入れ替えることも、別の抽選に使い回すこともできません。抽選の状態機械が再利用の防波堤です。各ステップは
抽選ごとに 1 回、精算はティアごとに 1 回だけ成功します。

## 区分と、ボールトがそれを追う方法

ある期間のプールの合計時間加重残高 `W` は暗号化されたままです。抽選が対象とする数値は `M = 2^m`、つまり `W` 以上で最小の
2 のべき乗です。

ボールトは `m` を毎回ゼロから計算するのではなく、抽選から抽選へ追跡します。クローズのたびに、前回の抽選の `m` の周辺にある
5 つの 2 のべき乗と `W` を暗号化したまま比較し、5 つの結果を 1 つの小さな暗号化されたカウントに足し合わせ、そのカウントを公開
復号可能にします。プールは検証済みのカウントを読んで新しい `m` を求めます。`m` は 1 抽選あたり最大 3 段階しか動けません。
1 との別の暗号化された比較が非空フラグを与えます。

したがって抽選ごとの公開の記録は小さな整数 1 つであり、それが変わるのはプールが 2 のべき乗をまたいだときだけです。プールの
`scaleBits()` が現在の `m` を返します。デプロイはこれを `initialScaleBits`、つまり最初の期間の合計の想定ビット長で初期化し、
追跡器が 1 抽選あたり最大 3 ビットずつ誤差を修正します。

## 誰でもしきい値を再計算する方法

以下はすべて公開データだけを使います。ウォレットも署名も権限も要りません。

抽選 `p`、預入者のアドレス `u`、賞の件数 `count[t]` と確率 `oddsNum[t] / oddsDen[t]` を持つティア `t` について、

```
prn         = keccak256(abi.encode(R, p, u, t))
r           = prn mod M                                        // 0 <= r < M
threshold_k = floor((r + k * M) * oddsDen[t] / (oddsNum[t] * count[t]))
```

を `0` から `count[t] - 1` までの各 `k` について計算します。その預入者が賞 `k` を当てたのは、期間 `p` のその人の時間加重ウェイトが
`threshold_k` より厳密に大きかったとき、かつそのときだけです。

自分で実装し直す必要はありません。ボールトは、評価が使うのと同じ計算を `thresholdOf(drawId, saver, tier, k)` という純粋な view
として公開しているので、アプリの検証パネル、テストスイート、ブロックエクスプローラを持つ誰もが同じ実装を読みます。コントラクトを
自分のコードと突き合わせたい場合、オフチェーンで実装し直すのは多倍長整数の演算 4 行です。

小さな数値での実例は[当選者の決定](../concepts/winner-selection.md)にあります。Sepolia の実際の抽選から取った、値の入った
実例をここに示します。`usdc` プールのもので、その賞金プールは `0xA0785AacF30B6FE46EDc53CD8A9db1d94FeF5Df2` です。どのプールも
自分の抽選について同じ項目を公開します。

| 項目 | 値 |
| --- | --- |
| 抽選 | `2、2026 年 9 月 2 日 23:00 から 00:00 UTC の期間` |
| シード `R` | `5625525180683981523` |
| 区分 `M` | `2^43、つまり 8,796,093,022,208 残高秒` |
| ハーベスト | `19.531380 USDC` |
| ティアごとの賞の金額 | `3.559644 / 1.779822 / 0.889911 USDC、グランド / ミッド / フリークエント` |
| ティアごとの支払い件数 | `0 / 0 / 5、賄える件数 2 / 2 / 8 に対して` |

チェーンからの読み取り方。シードと区分はプールの `DrawAwarded` イベントから、賞の金額と差し出された流動性は `drawParams(2)` から、
支払い件数はその抽選の 3 つの `TierReconciled` イベントから来ます。ティアが差し出して支払わなかった分は、そのティアが公開した
繰越額そのものだからです。この抽選でグランドとミッドのティアは何も支払わず、差し出した分を丸ごと返しました。24 分の 1 と 6 分の 1 の
ティアが、たいていの回にすることです。

アプリの検証パネルは、入力したどのアドレスについてもこの計算をブラウザ内で行います。見たいプールに応じて
`/verify?pool=<slug>` です。特権的なアクセスはありません。同じ公開の入力と同じ式です。

## 剰余に偏りがない理由

大きな乱数を単純な剰余である範囲に縮めると、通常は偏りが出ます。`2^256` がその範囲の正確な倍数でなければ、小さい剰余がわずかに
多く現れ、その偏りは預入者に不均等に降りかかります。PoolTogether V5 はこれを棄却サンプリングで解決しており、Hearth の初期の草案も
そうしていました。

Hearth にはもうその必要がありません。`M` は構成上 2 のべき乗であり、`2^256` は `2^256` までのすべての 2 のべき乗の正確な倍数です。
だから `prn mod M` は 256 ビットのハッシュの下位 `m` ビットそのものであり、`0` から `M - 1` までのどの値も、まったく同じ個数の入力から
生まれます。**偏りは小さいのではなくゼロ**であり、ループも棄却もなく、検証者が注意深く再現すべきものもありません。

これは正確な合計ではなく区分を公開したことの副産物であり、抽選を確かめる人が正確に一致させなければならなかったはずのコードを
1 つ取り除くので、書いておく価値があります。

## アドレスの総当たりは効かない

`R` が公開されたあと、しきい値の低いアドレスが見つかるまでアドレスを生成することはできます。しかし無意味です。しきい値は期間 `p` の
ウェイトと比較され、真新しいアドレスは期間 `p` 以前の観測値を持たないので、そのウェイトはゼロです。ゼロはどのしきい値も超えません。
期間 `p` にウェイトを持つには、期間 `p` の間に残高を保有している必要があり、その期間は `R` が存在する前に終わっています。

将来の抽選に向けた総当たりは別の理由で失敗します。その抽選のシードはまだ生成されておらず、予測不能だからです。

## 検証が証明することと、しないこと

ここを正確に述べることが、このページの目的です。

**証明すること:**

- シードはチェーン上で、トランザクションの内部で、ネットワークの鍵のもとに生成され、ちょうど 1 回だけ公開されたこと。
- 賞の金額と差し出された流動性は、そのシードが存在する前に確定していたこと。
- すべての預入者に適用されたルールは公開であり、一様であり、誰でも再計算できること。
- 賞の金額が、ティアの流動性とティアのパラメータから公開の計算で導かれること。
- 各ティアが支払った賞の件数が、そのティアが差し出した額から繰越額として戻った額を引いたものと一致すること。
- ボールトが書いたすべての付与にプールが資金を出したこと。未充当カウンタが公開されており、ゼロだからです。

**証明しないこと:**

- コプロセッサのジェネレータが一様であること。それは Zama のエンジンであり、ここでは検証ではなく信頼の対象です。
- 鍵管理サービスがシードのハンドルの真の平文に署名したこと。コントラクトが検査するのは署名であって意味ではありません。不誠実な
  クォーラムは自分の選んだ値に署名できます。このプロトコル上のすべてのアプリケーションがこの前提を共有しており、
  [脅威モデル](threat-model.md)の攻撃者 8 です。
- 公開された区分が、本当にすべての預入者のウェイトの合計の区分であること。外部の人は暗号化されたウェイトを足し合わせられませんし、
  いまはその合計を見ることもできません。代わりにあるのは、同じ公開の、変更不能なコードが、同じ観測値から比較と各預入者のウェイトを
  計算したという事実と、保存の不変条件が成り立っているという事実です。支払いは付与に等しく、誰も元本と当選金の合計を超えて引き出せません。
- 誰が当たったかについては何も証明しません。それこそが要点であり、だからこそもっと公開すれば検証は強くなり、製品は悪くなります。
  正確な合計の公開が具体例です。それはプールの規模を検証可能にしましたが、同時に単独でお金を動かした人の預入額を基本単位まで復元
  可能にもしました。

## 預入者だけが確かめられること

預入者は外部の人より 1 歩先まで行けます。その抽選での自分のウェイトと自分の付与額を復号できるからです。

1. 抽選 `p` での自分のウェイトを開示します。
2. 公開された `R` と `M` から自分のしきい値を再計算するか、`thresholdOf` から読みます。
3. いくつ超えたかを数え、そのティアの賞の金額を掛けます。
4. 抽選 `p` での自分の付与額を開示し、一致するかを確かめます。

一致しない場合、巡回が到達する前にティアが尽きたか、これは記録済みの丸めです、あるいは何かがおかしいのであり、そのときあなたは
それを証明する数値を持っています。アプリはこの 4 ステップを代わりに行い、計算を表示します。

# キーパー

抽選はひとりでに起きるわけではありません。何かがトランザクションを送る必要があります。このページは、その何かが行うこと、
止まったときに起きること、そしてかかる費用です。

1 つのプロセスが 1 つのプールを動かします。Hearth は Sepolia で 7 つのプールを動かしているので、キーパープロセスも 7 つ動き、
それぞれが同じシードフレーズの別々のアカウントから署名し、それぞれが 1 つのプールのアドレスファイルを見ています。下の
「プールごとに 1 つのキーパー」の節がその表です。

まず大事な位置づけから。キーパーに特権はありません。呼び出す関数はどれも誰でも呼べますし、キーパーが悪用しえた 2 つのレバー、
つまり誰が評価されるかを選ぶことと支払いの順序を選ぶことは、もはやレバーではありません。預入者の手間を省く便宜であって、安全性が
それに依存する役職ではありません。

## 抽選 `p` についての仕事、順番に

1. **クローズ。** 期間 `p` が終わったあと、`closeDeadline(p)`、つまり期間 `p+2` の中間点より前に `closeDraw(p)` を呼びます。
   期間 `p+1` の早いうちにやるのが良い習慣です。これは各ティアの賞の金額と差し出す流動性を確定し、その流動性を抽選に移し、
   暗号化されたシードを引き、ボールトに暗号化されたスケールカウントと非空フラグを求め、イールドソースをハーベストし、4 つの
   ハンドルすべてを公開復号可能にします。
2. **証明を取得する。** Zama のリレイヤーに、4 つのハンドルを `[seed, scaleCount, nonEmpty, harvested]` の順で公開復号する
   よう求めます。リレイヤーは鍵管理サービスの署名を付けて平文を返します。
3. **授与。** `awardDraw(p, seed, scaleCount, nonEmpty, harvested, proof)` を呼びます。コントラクトが署名をチェーン上で検証し、
   ハーベストを各ティアに計上し、抽選を開きます。当選者はこの瞬間に決まります。
4. **評価。** ボールトの `evaluate(p, count)` を、巡回が出発点まで一周するまで繰り返し呼びます。呼び出しごとに、シードから
   導かれた開始地点から預入者リストを進む抽選ごとのカーソルが前進します。キーパーが選ぶのは `count` であって、どのアドレスかでは
   ありません。`4` が、暗号化処理を要する預入者として 1 トランザクションに入る最大人数です。
   期間 `p` 以前の観測値を持たない預入者は、コントラクト自身が平文のタイムスタンプから、暗号化コストなしでスキップします。
5. **ファイナライズ。** 期間 `p+2` の終わりでウィンドウが閉じたあと、`finalizeDraw(p)` を呼びます。これは各ティアの未払いの
   残りをそのティアの暗号化された繰越額に折り込み、未充当カウンタを公開し、精算の番が来たティアについてはその繰越額を公開復号
   可能にして `CarryPublished` を出します。
6. **番の来たティアごとに精算。** `finalizeDraw` が公開した各ティアについて、繰越額の平文を取得し、`reconcile(tier, carry, proof)`
   を呼びます。プールは、ボールトが公開したハンドルに対して証明を検査し、検証済みの数値をそのティアの平文流動性に計上します。
   ボールトは、公開後に増えているかもしれない繰越額からその分を差し引き、`TierReconciled` が出ます。

Sepolia ではどのプールのどのティアも毎回の抽選が対象なので、ステップ 6 はファイナライズのたびに最大 3 回走ります。頻度は
ティアごとのコンストラクタ引数であり、キーパーはそれを決め打ちせずチェーンから読むので、繰越額の公開頻度が少ないデプロイでも
キーパーを変える必要はありません。このデプロイが 3 つとも毎回公開している理由は
[賞金とティア](../concepts/prizes-and-tiers.md)にあります。

## 順序のルール

**抽選 `p` のファイナライズと精算は期間 `p+3` の始めに、同じ期間で抽選 `p+2` をクローズする前に行います。**

理由は正しさではなくお金です。クローズは各ティアの賞の金額をその時点の平文流動性から決め、精算は以前の抽選の繰越額を平文流動性に
戻す手順です。先に精算すればそのお金はすぐ賞の金額に反映され、あとで精算すれば 1 抽選ぶん待つことになります。

どちらの仕事も同じ瞬間に可能になります。抽選 `p` のウィンドウは期間 `p+2` の終わりで閉じ、抽選 `p+2` は期間 `p+3` の始めに
クローズ可能になるので、キーパーはファイナライズと番の来た精算を先に済ませ、それからクローズします。

順序がずれても失われるものはありませんが、どちらにずれるかは重要です。ファイナライズより先にクローズすると、そのティアの繰越額は
まだ保留中ではないので `openDraw` がそれを差し出し分に折り込み、そのお金はまだ当てられます。ただ公開される賞の金額は上がりません。
`closeDraw` は賞の金額を平文流動性だけから確定するからです。ファイナライズ、クローズ、精算の順にすると繰越額は保留中になります。
`openDraw` は保留中の繰越額を抽選からまるごと外すので、そのお金は精算がフラグを解くまで差し出されも当てられもしません。Sepolia では
どのファイナライズでも全ティアが対象なのでこれが通常のケースであり、だからこそキーパーはファイナライズのあとに繰越額を読み直し、
クローズの前に精算します。どちらにしても失われるものはありません。精算のあとの最初のクローズが、その全額を折り込みます。

## キーパーが止まったときに起きること

何も失われません。それが答えのすべてであり、それが成り立つのは、実行されなかったステップの扱い方によるものです。

| 実行されなかったステップ | 帰結 |
| --- | --- |
| クローズが行われない、または `closeDeadline` のあとに行われて失敗する | 抽選は `None` のままスキップされます。流動性は動かされていないのでティアに残り、次の抽選で差し出されます。ハーベストは次のクローズで回収されます。 |
| ウィンドウ内に授与が行われない | 遅れた授与でもハーベストは計上され、差し出された流動性はティアに戻り、抽選は `Skipped` になります。利回りも流動性も消えません。 |
| 巡回が全預入者に到達しない | 巡回が届かなかった預入者はその抽選から何も得ません。その人の差し出し分に占める割合は、ファイナライズでティアの繰越額に折り込まれ、また差し出されます。実在する預入者が得られたかもしれないものを失う唯一のケースであり、制約 2 です。 |
| ファイナライズや精算が遅れる | ティアの平文流動性がしばらく少なくなるので、賞の金額が小さくなります。ファイナライズが公開し、まだ精算が解消していない繰越額は、精算が着地するまでどのクローズにも入りません。失われるものはありません。精算のあとの最初のクローズが全額を折り込みます。 |

キーパーが止まると、プールは抽選を失いますが、お金は失いません。預け入れと引き出しはその間も動き続けます。一時停止の経路がそれらに
触れることはなく、止まった抽選が何かをロックすることもないからです。

私たちの旧デプロイが戒めの例です。`openDraw` はパーミッションレスでしたが誰も呼ばなかったので、稼働中のプールは開ける状態の抽選を
抱えたまま 26 時間座っていました。パーミッションレスは自動化と同じではありません。だからこの設計には本物のキーパーがあり、その下に
冗長の経路があります。

## 預入者が自分で抽選を進める方法

上のすべてのステップはパーミッションレスであり、アプリはその全部を「抽選を実行」の画面、いまいるプールの `/app/<slug>/run` に
出しています。サイドバーで「誰でも」と書かれた行です。上部のカードがプールが待っているステップを示し、その下の 5 つがそれぞれ
自分のボタンを持ちます。そのステップの番でないときは、理由を示して無効になります。

- **クローズ**、続いて**授与**。クローズは賞の金額を確定し、暗号化されたシードを引きます。授与はブラウザ内で 4 つの復号証明を
  取得し、署名された平文を送り返します。リレイヤーへの呼び出しはキーパーが行うものと同じで、SDK がページから実行します。
- **進める。** いま開いている抽選について `evaluate(p, count)` を実行し、共有の巡回を 1 バッチぶん進めます。同じ呼び出しが
  「マイ抽選」の自分の抽選カードに「抽選を進める」として置かれています。キーパーが止まっていて巡回がまだ自分に届いていないときに
  押すボタンです。自分を選ぶことはできませんが、それが利点です。誰も自分だけを取り出せないので、このトランザクションを送っても
  当選したかどうかは何も伝わりません。
- **ファイナライズ**と**精算。** ウィンドウが終わった抽選について、締めの 2 ステップを実行します。

どれも私たちの許可も、鍵も、サーバーの稼働も必要としません。

## Chainlink Automation、クローズのステップだけ

`HearthPrizePool` は、クローズのステップについて Chainlink の `checkUpkeep` と `performUpkeep` のインターフェースを実装しています。
時刻ベースの upkeep を登録すれば、抽選を予定どおりクローズする 2 つ目の独立した経路がプールに与えられますし、クローズは期限を持つ
ステップなので、保険をかける価値があるのはそこです。

対象はクローズだけであり、理由は単純です。クローズはオフチェーンのデータを必要としない唯一のステップです。授与には Zama のリレイヤー
から取得する復号証明が要ります。評価はカーソルが一周するまで繰り返す必要があります。精算にはもう 1 つの復号が要ります。チェーン上の
自動化ネットワークはそのどれも取得できないので、できるふりをすれば見せかけになります。

この upkeep は任意です。登録した upkeep アカウントに LINK が要りますし、主経路ではなく冗長であり、プールごとに 1 つ、それぞれの
スケジュールで登録することになります。7 つのどれにもまだ登録されていないので、デモのプールを動かしているのはキーパーだけです。

セレクタ 2 つのために Chainlink のコントラクトパッケージとその依存関係をまるごと追加するのではなく、この 2 関数のインターフェースを
ローカルに宣言しています。

## 予算

稼働中のデプロイから取った、1 抽選あたりの費用です。

| ステップ | 1 抽選あたりのトランザクション数 | 1 回あたりのガス |
| --- | --- | --- |
| クローズ | 1 | `1,422,474` |
| 授与 | 1 | `435,578` |
| 評価、4 人のフルバッチ | `floor(savers / 4)`、ここでは 1 | `3,417,699` |
| 評価、最後の端数バッチ | 0 か 1、ここでは 1 人を運ぶ 1 回 | 1 人で `1,291,192`、追加 1 人ごとに `708,836` |
| ファイナライズ | 1 | `509,463` |
| 精算 | 3、ティアごとに 1 回。どのティアも毎回の抽選が対象だからです | `459,994` |

預入者 5 人ではこれで 1 抽選あたり `8,456,388` ガス、デプロイ時の Sepolia の基本手数料である 1 gwei でおよそ `0.0085 ETH` です。
1 時間の期間なら 1 日 24 回で `0.2030 ETH`、1 日の期間なら `0.0085 ETH` です。

これに 7 プールを掛けたものが、6 つのプールが 1 時間ごとではなく 6 時間ごとに抽選する理由のすべてです。7 つすべてを 1 時間ごとに
すると 1 日 168 回、およそ `1.43 ETH` になり、公開フォーセットでは追いつけません。1 時間プール 1 つと 6 時間プール 6 つなら 1 日
48 回、およそ `0.41 ETH` です。キーパーのアカウントはそれぞれ別に資金を入れるので、ガスが尽きたプールは自分の抽選だけを止めます。

バッチに預入者を 1 人追加すると Sepolia で `708,836` ガス、1 人だけを運ぶバッチは `1,291,192` です。呼び出しの固定部分はどちらにせよ
支払うからです。コンピュートユニットで見ると預入者 1 人は `3,674,128` で、これはモックコプロセッサの価格表での数値です。そこでしか
読めないのは、本番のレシートがコンピュートユニットを報告しないからです。バッチサイズ `4` は、この実測値を、Zama が公表している
Sepolia の上限、1 トランザクションあたり 20,000,000 コンピュートユニット、うち逐次深さ 5,000,000 に照らして決めたものです。
`evaluate` は任意の数を受け取るので、Zama が演算の価格を改定してもキーパーは再デプロイなしに小さなバッチに落とせます。

**キーパーは巡回を最後まで評価します。** 評価にいくらかかるかをチェーン上で制限するものはなく、キーパーも途中で止めません。
キーパーが課すのは手数料の上限（`KEEPER_MAX_FEE_GWEI`）であり、それを下回る間はカーソルが終わりに達するまで送り続けます。
誠実な帰結は[脅威モデル](../security/threat-model.md)に述べたとおりです。価値のないアドレスで水増しされたプールは、預入者から賞を
奪うのではなく、キーパーの 1 抽選あたりのガス代を増やします。期間より前の観測値がないアドレスは、暗号化処理なしでスキップされる
からです。キーパーが止まっているときは誰でも「進める」を押せますし、巡回は毎回違う地点から始まるので、恒久的に最後尾に座る人は
いません。

## プールごとに 1 つのキーパー

プロセスがどのプールを動かすかは
`HEARTH_ADDRESSES_FILE`、つまりそのプールのデプロイが書いたアドレスファイルで指定します。このファイルはトークンのシンボル、桁数、
署名に使うアカウントインデックスも与えます。`KEEPER_NAME` は、すべてのログ行に付くタグです。
`packages/keeper/ecosystem.config.cjs` は 1 台のマシンで、pm2 のもとに 7 つすべてを 1 プロセスずつ起動します。

| pm2 のプロセス | `HEARTH_ADDRESSES_FILE` | `KEEPER_ACCOUNT_INDEX` |
| --- | --- | --- |
| `hearth-keeper-usdc` | `hearth.json` | 1 |
| `hearth-keeper-usdt` | `hearth.usdt.json` | 10 |
| `hearth-keeper-weth` | `hearth.weth.json` | 11 |
| `hearth-keeper-bron` | `hearth.bron.json` | 12 |
| `hearth-keeper-zama` | `hearth.zama.json` | 13 |
| `hearth-keeper-tgbp` | `hearth.tgbp.json` | 14 |
| `hearth-keeper-xaut` | `hearth.xaut.json` | 15 |

`usdc` のプロセスが `hearth.usdc.json` ではなく `hearth.json` を見ているのは、それが最初のデプロイが書いたファイルであり、当時は
プールにスラッグがなく、稼働中のキーパーが何日もそれを見てきたからです。両方のファイルは同じアドレスを持ちます。

インデックスを飛ばして割り当てているのは、あとからプールを追加しても番号を振り直さずに済むようにするためで、各アカウントには
それぞれ Sepolia ETH が必要です。インデックス 0 はデプロイヤーであり、キーパーはそれを拒否します。

## 稼働中の 7 つがどこで動いているか

ノート PC の pm2 で 7 つすべてを動かすのも一つのやり方で、今でも動きます。cUSDC のキーパーは Railway 上で動いています。残りの 6 つは、
それぞれの Railway サービスができるまで pm2 の下で動いています。プールごとに 1 サービスにすれば、ノート PC を閉じても抽選は止まりません。

キーパーはスケジュール実行の関数ではなく、長時間動き続けるプロセスです。1 回のパスで鍵管理サービスの応答を 2 分待つことがあり、
これはたいていのサーバーレス基盤が許す時間より長いからです。Node のプロセスを生かしておけるホストならどれでも構いませんが、
リポジトリにはこのホスト向けの設定が入っています。

- リポジトリのルートにある `railway.json` は、`usdc` のサービスがそこから作られたものです。
- `railway/hearth-keeper-<slug>.json` には、残り 6 つそれぞれの値が記録してあります。Railway は新しいサービスで設定ファイルを読まなく
  なったので、それらの値はサービス自身の設定に入れます。ここに示したビルドコマンドと起動コマンド、そして `RECOVERY_PHRASE`、
  `SEPOLIA_RPC_URL`、`HEARTH_ADDRESSES_FILE`、`KEEPER_ACCOUNT_INDEX`、`KEEPER_NAME` を変数として設定します。

どのホストでも、ビルドは `npm run build -w @hearth/keeper`、起動は `node packages/keeper/dist/src/index.js` です。キーパーが必要と
するコントラクトの ABI は `packages/keeper/abi` にコミットしてあるので、コントラクトを一度もコンパイルしないホストでも動きます。
さらに起動時のチェックが、読み込んだ ABI とキーパーが呼ぶ関数を突き合わせるため、ずれは最初のトランザクションではなく起動時に
報告されます。アドレスファイルも同じ理由でコミットが必要で、実際に `packages/contracts/deployments/sepolia/` にコミットしてあります。

どこで動かすにせよ、1 プールにつき 1 プロセスだけにしてください。1 つのアカウントから署名するキーパーが 2 つあると、同じノンスを
奪い合います。同じプールでホスト上のものを起動する前に、ローカルのものを止めてください。サービスごとの手順は、キーパーパッケージ
自身の README、`packages/keeper/README.md` にあります。

## 実行方法

キーパーは `@hearth/keeper` パッケージです。デプロイと同じ `RECOVERY_PHRASE` の 1 アカウントで署名し、`SEPOLIA_RPC_URL` を
`packages/contracts/.env` から読みます。キーパー自身の設定は `packages/keeper/.env` にあります。

```
HEARTH_ADDRESSES_FILE=../contracts/deployments/sepolia/hearth.weth.json
KEEPER_ACCOUNT_INDEX=11            # defaults to the index in the address file
KEEPER_NAME=weth                   # defaults to the slug in the address file
KEEPER_BATCH=4                     # savers of encrypted work per evaluate call
KEEPER_POLL_SECONDS=30
KEEPER_MAX_FEE_GWEI=20             # refuse to send above this
```

```
npm run compile -w @hearth/contracts    # the keeper reads the compiled ABI
npm run build -w @hearth/keeper
npm run plan -w @hearth/keeper          # one pass, simulates every call, sends nothing
npm run once -w @hearth/keeper          # one live pass
pm2 start packages/keeper/ecosystem.config.cjs   # all seven
pm2 logs hearth-keeper-weth                      # one pool
```

`plan` と `once` は `HEARTH_ADDRESSES_FILE` が指すプールを動かすので、別のプールを確かめるにはコマンドの前に変数を 1 つ付けるだけ
です。単一プール構成の名残で `HEARTH_VAULT` と `HEARTH_POOL` が `packages/keeper/.env` に残っている場合は消してください。アドレス
ファイルより先に読まれるので、7 つのプロセスすべてが 1 つのプールを動かしてしまいます。

1 回のパスは 1 つの事実につき 1 行を記録し、すべての行にそのプロセスが動かすプールのタグが付くので、7 つのログが混ざっても読めます。
金額にはそのプール自身のシンボルと桁数が付き、どちらもアドレスファイルから読みます。

```
09:14:37 [usdc] closed draw 41 (gas 1,422,474)
09:14:39 [usdc] draw 41: asking the relayer for the seed, the scale, the empty flag and the harvest
09:14:53 [usdc] awarded draw 41: 3 tiers, prizes 12.40 / 2.10 / 0.40 cUSDC, harvest 3.60 cUSDC (gas 435,578)
09:15:07 [usdc] evaluated draw 41: 4 of 9 savers done (gas 3,417,699)
09:15:38 [usdc] nothing to do: period 43, draw 41 has 8 of 9 savers evaluated
```

WETH のプロセスは同じ行を `[weth]` のもとに、`cWETH` で出します。どの種類の行が何を意味するかは、行ごとにキーパーパッケージ自身の
README、`packages/keeper/README.md` にあります。

キーパーはティックとティックの間に状態を持ちません。抽選の状態、評価のカーソル、精算の頻度をチェーンから読み、何をすべきかを導き
ます。再起動しても失われるものはありません。プールごとにちょうど 1 インスタンスを動かし、1 つのアカウントで 2 つを動かさないで
ください。チェーン上では各ステップは抽選ごと、ティアごとにちょうど 1 回しか成功せず、2 つの evaluate 呼び出しは同じカーソルを進める
だけですが、1 つのアカウントの 2 つのキーパーはトランザクションの nonce を奪い合います。

## このページが扱わないこと

キーパーのトランザクションがお金に対して実際に何をするかは扱いません。それは[抽選の仕組み](../concepts/how-a-draw-works.md)です。
デプロイも扱いません。それは[デプロイ](deploying.md)です。そして可用性の約束はしません。私たちはキーパーを動かしますが、保証はせず、
保証しないことが受け入れられるように設計されています。
